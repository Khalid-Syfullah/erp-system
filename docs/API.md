# ERP System — API Specification

Status: **Approved baseline (Phase 1)**.

This document defines the conventions every endpoint MUST follow, and the resource catalogue. The machine-readable contract is the OpenAPI 3.1 document generated by springdoc at `/api/v1/openapi.json`. It is non-public in production and published as a CI artifact. That generated document must be consistent with this specification.

Related: [ARCHITECTURE.md](ARCHITECTURE.md) · [SECURITY.md](SECURITY.md) · [PRODUCT_SPEC.md](PRODUCT_SPEC.md)

---

## 1. Principles

- **Resource-oriented JSON over HTTPS.** There is no GraphQL in v1.
- **The backend is the authority.** It validates and authorizes everything and computes all derived amounts.
- **State changes are explicit actions.** You transition a document with `POST /…/{id}/confirm`, `/post` and so on. You never change state with `PATCH {"status": "POSTED"}`.
- **Every write is one transaction** (§15).
- **Contract-first discipline.** Request and response DTOs are separate Java records in each module's `web` package. Domain objects are never serialized directly.

## 2. Versioning

- The URI major version is `/api/v1`. A new major version is introduced only for breaking changes. The old version is kept for at least 6 months after the new one is released, and deprecated endpoints return `Deprecation` and `Sunset` headers (RFC 8594/9745).
- **Additive changes are non-breaking:** new optional request fields, new response fields, new endpoints and new enum values. Clients MUST ignore unknown response fields and MUST handle unknown enum values gracefully.
- Event schemas follow their own versioning (ARCHITECTURE.md §5.1).

## 3. URL structure

```
/api/v1/auth/...                               authentication (no company)
/api/v1/me                                     current user, preferences, accessible companies
/api/v1/admin/...                              global administration (system admin only)
/api/v1/reference/...                          global reference data (currencies, countries, uoms)
/api/v1/companies                              companies the caller can access
/api/v1/companies/{companyId}/...              company-scoped resources (everything else)
```

- **Company scoping is in the path.** For every `/companies/{companyId}/**` request, the authorization layer verifies that the caller has an active role assignment in `{companyId}` **before** the controller runs, and sets the request and DB context (ARCHITECTURE.md §6.3). If there is no assignment, the response is `404 Not Found`, not 403, so that company existence is not disclosed.
- **Resource naming:**
  - lowercase, plural, kebab-case nouns (`/sales-orders`, `/purchase-orders`, `/journal-entries`)
  - sub-resources for composition (`/sales-orders/{id}/lines`)
  - module prefixes only where needed to disambiguate (`/companies/{c}/inventory/...` is **not** used; names are unique across modules)
- **IDs** in paths are UUIDs. Malformed IDs return `404`, not `400`, to avoid enumeration oracles. Human-readable numbers can be looked up with `?filter[number]=INV-2026-000123`.

## 4. HTTP methods and semantics

| Method | Use | Idempotent | Notes |
|---|---|---|---|
| `GET` | Read a resource or list | yes | Never changes state (except `last_used_at` style metadata). |
| `POST /collection` | Create (usually a DRAFT) | no → make it so with `Idempotency-Key` | Returns `201` + `Location` + body + `ETag`. |
| `PATCH /resource/{id}` | Partial update of a mutable (DRAFT) resource | yes with `If-Match` | **JSON Merge Patch** (RFC 7396), `Content-Type: application/merge-patch+json`. To replace line collections, use the sub-resource endpoints. |
| `PUT /resource/{id}/...` | Full replacement, only for settings-like singletons (e.g. `/settings/inventory`) | yes | Requires `If-Match`. |
| `DELETE /resource/{id}` | Delete a DRAFT document, or deactivate is **not** done by DELETE (see below) | yes | Returns `204`. For non-drafts, the response is `409 INVALID_STATE`. |
| `POST /resource/{id}/{action}` | State transition or command (`submit`, `approve`, `reject`, `confirm`, `post`, `cancel`, `reverse`, `void`, `close`, `reopen`, `allocate`, `deactivate`, `activate`, ...) | via `Idempotency-Key` | Requires `If-Match`. Returns `200` with the updated resource, or `202` for async commands. |

Master data is never deleted once referenced. It is deactivated with `POST /…/{id}/deactivate`. `DELETE` on master data succeeds only when the record is unreferenced; otherwise it returns `409 RESOURCE_IN_USE`.

## 5. Status codes

| Code | When |
|---|---|
| 200 | Successful GET, PATCH or action that returns a body |
| 201 | Created (POST to a collection) |
| 202 | Accepted async command (returns a job resource) |
| 204 | Success with no body (DELETE, logout) |
| 400 | Malformed request: unparseable JSON, wrong types, unknown query parameters for filters/sort (`BAD_REQUEST`) |
| 401 | Not authenticated, or session expired (`UNAUTHENTICATED`) |
| 403 | Authenticated but lacking the permission for a resource the caller **can see** (`FORBIDDEN`), or a CSRF failure (`CSRF_INVALID`) |
| 404 | Not found, **or not visible** to the caller (other company or branch out of scope) |
| 409 | Conflict: version mismatch (`VERSION_CONFLICT`), invalid state transition (`INVALID_STATE`), duplicate (`DUPLICATE_*`), resource busy or lock timeout (`RESOURCE_BUSY`), or idempotency key reused with a different payload (`IDEMPOTENCY_KEY_REUSED`) |
| 412 | `If-Match` does not match the current version (`PRECONDITION_FAILED`) |
| 413 | Payload or upload too large |
| 415 | Unsupported content type |
| 422 | Semantically invalid: field validation (`VALIDATION_FAILED`) or business rule violation (e.g. `INSUFFICIENT_STOCK`, `PERIOD_CLOSED`, `CREDIT_LIMIT_EXCEEDED`, `ACCOUNT_MAPPING_MISSING`) |
| 428 | `If-Match` required but missing (`PRECONDITION_REQUIRED`) |
| 429 | Rate limited (`RATE_LIMITED`), with a `Retry-After` header |
| 500 | Unexpected error (`INTERNAL_ERROR`), with the request ID only |
| 503 | Maintenance or dependency unavailable (`SERVICE_UNAVAILABLE`) |

**404 versus 403 rule.** If the caller cannot **read** a resource (wrong company or branch, or no read permission for that resource type), the response is 404. If the caller can read it but lacks the permission for the requested **action**, the response is 403.

## 6. Error format (RFC 9457 Problem Details)

`Content-Type: application/problem+json`

```json
{
  "type": "urn:erp:problem:insufficient-stock",
  "title": "Insufficient stock",
  "status": 422,
  "code": "INSUFFICIENT_STOCK",
  "detail": "Not enough available stock to post delivery DEL-2026-000045.",
  "instance": "/api/v1/companies/0190.../deliveries/0191.../post",
  "requestId": "01J9Z6K8T6M1V8Q2ZJ5R1Y3B7C",
  "errors": [
    {
      "pointer": "/lines/2/quantity",
      "code": "INSUFFICIENT_STOCK",
      "message": "Requested 10 EA, available 4 EA at WH1/STOCK",
      "meta": { "variantId": "0190...", "locationId": "0190...", "requested": "10", "available": "4" }
    }
  ]
}
```

- `type` is the URN `urn:erp:problem:<code in kebab-case>`. It identifies the problem type and is not meant to be dereferenced.
- `code` is a stable, documented UPPER_SNAKE_CASE identifier. Clients branch on `code`, never on `title` or `detail`.
- `errors[].pointer` is a JSON Pointer (RFC 6901) into the request body, or `parameter` for query parameters (`{"parameter": "filter[status]"}`).
- `detail` and `message` are human-readable English. They contain no internal identifiers beyond what the caller can see, no SQL, and no stack traces.
- The error code catalogue is maintained in `platform.web.ErrorCode`: platform codes are in `PlatformErrorCode`, and modules define their own enums. It will be published in the OpenAPI document (`x-error-codes`) once OpenAPI generation is added.
- `errors[]` entries use these field-level codes:
  - **Body (`pointer`):** `UNKNOWN_PROPERTY`; `INVALID_VALUE` (wrong JSON type or format); and the Bean Validation constraint in UPPER_SNAKE_CASE, e.g. `NOT_BLANK`, `SIZE`, `POSITIVE`, `DECIMAL_MIN`.
  - **Query and headers (`parameter`):** `UNKNOWN_PARAMETER`, `DUPLICATE_PARAMETER`, `REQUIRED`, `INVALID_VALUE`, `OUT_OF_RANGE`, `UNSUPPORTED_SORT`, `DUPLICATE_SORT`, `UNSUPPORTED_FILTER`, `UNSUPPORTED_OPERATOR`, `TOO_MANY_VALUES`, `INVALID_CURSOR`, `STALE` (If-Match).
- Problems are produced the same way for errors raised outside Spring MVC: by servlet filters, by Spring Security (401/403), and by the container (`/error`).

## 7. Validation

- **Shape validation** (types, required fields, lengths, formats, ranges) uses Bean Validation on request DTOs. Failures return `422 VALIDATION_FAILED` with **all** field errors at once.
- **Business validation** happens in domain and application code. It returns a specific `code`, or `VALIDATION_FAILED` with per-field errors when several rules fail.
- Malformed JSON, wrong JSON types and unknown properties return **400 `BAD_REQUEST`** with a pointer. Values that parse but violate constraints return **422 `VALIDATION_FAILED`**.
- Unknown JSON properties, duplicate keys and trailing content are **rejected** with `400`. Scalars are never coerced: `"5"` is not an integer, `1.5` is not an integer, and `"true"` is not a boolean. This prevents mass-assignment and catches client bugs. Read-only fields (`id`, `number`, `status`, totals, `version`, audit fields) are not part of create or update DTOs.
- Strings are trimmed, then checked for max length. Control characters (C0 except tab, LF and CR; DEL; C1) are rejected in every string. Fields that must not contain line breaks enforce that with their own constraint.
- Enums are case-sensitive and UPPER_SNAKE_CASE.

## 8. Lists: pagination, filtering, sorting and search

### 8.1 Pagination

**Cursor (keyset) pagination** is the default for all lists:

```
GET /api/v1/companies/{c}/sales-orders?limit=50&cursor=eyJrIjpbIjIwMjYtMTAtMDEiLCIwMTkw..."]}
```

Response envelope:

```json
{
  "data": [ { ... }, ... ],
  "page": { "limit": 50, "nextCursor": "eyJ...", "hasMore": true },
  "meta": { "totalCount": 1234 }
}
```

- `limit` defaults to 25, with a maximum of 200.
- The cursor is opaque: a base64url binary payload (format version, query fingerprint, the sort-key values plus a unique tiebreaker) followed by its HMAC-SHA256 signature. The key is `ERP_API_CURSOR_SIGNING_KEY`. A cursor is valid only for the same filters, sort and search; otherwise the response is `400 INVALID_CURSOR`.
- `meta.totalCount` is computed only when `includeTotal=true` is requested, because it can be expensive. Otherwise it is `null`.
- **Unknown or repeated query parameters are rejected** with `400`. Problems are reported all at once, one `errors[]` entry per parameter.
- Lists use cursor pagination even when small, including reference data.

### 8.2 Filtering

- Syntax is `filter[field]=value` for equality, and `filter[field][op]=value` with these operators:
  - `eq`, `ne`
  - `gt`, `gte`, `lt`, `lte` (numbers and dates)
  - `in` (comma-separated)
  - `like` (case-insensitive *contains*; `%` and `_` are matched literally; STRING fields only)
  - `isNull` (`true`/`false`)
- Example: `filter[status][in]=CONFIRMED,PARTIALLY_DELIVERED&filter[orderDate][gte]=2026-01-01&filter[customerId]=0190...`
- **Only allowlisted fields can be filtered.** Each list endpoint documents its filterable fields. Unknown fields return `400`. Filters are compiled into parameterized jOOQ conditions; string interpolation into SQL is never used.
- **Effective-dated lists** (employment assignments, department heads) also accept `asOf=yyyy-MM-dd`, which keeps only the rows in effect on that date (`effectiveFrom ≤ asOf ≤ effectiveTo`, open end included).

### 8.3 Sorting

- `sort=field1,-field2`, where `-` means descending. Only allowlisted fields can be sorted. Sortable columns must be NOT NULL, because keyset pagination needs a total order. A unique tiebreaker (`id`, or the natural key for reference data) is always appended.
- Each endpoint documents its default sort, typically `-createdAt` for documents and `code` for master data.

### 8.4 Search

`q=<text>` runs a quick search over the endpoint's documented search fields: number, code, name, SKU, barcode and partner name. It is case-insensitive and uses `pg_trgm` and prefix indexes. The minimum length is 2 characters.

## 9. Concurrency: ETag and If-Match

- Every single-resource response includes `ETag: W/"<version>"`. The body also includes `version`.
- `PATCH`, `PUT`, `DELETE` and **all action endpoints** require `If-Match`. A missing header returns `428`. A mismatch returns `412`, and the current representation is available through GET.
- When the version check happens inside the transaction (`UPDATE … WHERE version = ?` affects 0 rows), the response is `409 VERSION_CONFLICT`. The client treats `409 VERSION_CONFLICT` and `412` the same way: reload, then retry or merge.
- Sub-resource line endpoints use the **parent's** version. Any line change increments the header version.

## 10. Idempotency

- `Idempotency-Key: <uuid or 8–128 char token>` is **required** on:
  - `POST` create of documents that may post immediately: payments, expenses, journal entries with `postImmediately`, stock adjustments with `postImmediately`.
  - All `POST` action endpoints that post, approve, pay, void, reverse or allocate.

  It is **optional but honored** on the other POSTs of business documents that run through the idempotency executor (ADR-035). From Phase 5 that is stock movement creation; from Phase 6 the `[I]` endpoints of Procurement; Sales and Accounting add theirs. Master-data POSTs ignore the header.
- Keys match `^[A-Za-z0-9_.:-]{8,128}$`; a missing key on a `[I]` endpoint or a malformed key is `400 BAD_REQUEST`.
- Behaviour, per (authenticated principal, key), stored in `platform.idempotency_keys` for 24 hours (purged hourly):
  - **First request:** record it as IN_PROGRESS with a request hash (SHA-256 of method, path, query and the canonical JSON body with sorted keys), execute it, then store the status, the `ETag` and `Location` headers and the body (verbatim) as COMPLETED **in the same transaction** as the business change. On a failure response with a 4xx code, the business change rolls back and the key is then stored with that response in its own transaction, except `RESOURCE_BUSY` and the `IDEMPOTENCY_*` codes, which stay retryable. On a 5xx response or a transaction rollback, the key row is rolled back, so a retry executes again. Serialization failures and deadlocks are retried up to three times before answering (ARCHITECTURE.md §6.2).
  - **Same key and same hash, COMPLETED:** replay the stored response with the header `Idempotent-Replayed: true`.
  - **Same key, different hash:** `409 IDEMPOTENCY_KEY_REUSED`.
  - **Same key, still IN_PROGRESS:** `409 IDEMPOTENCY_IN_PROGRESS`. A concurrent duplicate blocks on the key row and then sees the result.
- Clients generate a new key per user intent and reuse it on network retries.

## 11. Data formats

| Kind | Format | Example |
|---|---|---|
| IDs | UUID string (v7) | `"0192a1b2-..."` |
| Money amounts | **Decimal string**, never a JSON number | `"1234.50"` |
| Money with currency | Object | `{"amount": "1234.50", "currency": "USD"}` (headers use a `currencyCode` field plus plain amount strings to avoid repetition) |
| Quantities, prices, rates, percentages | Decimal string | `"12.500000"`, `"0.9150000000"`, `"12.5"` |
| Dates | ISO 8601 `YYYY-MM-DD` | `"2026-10-02"` |
| Timestamps | ISO 8601 UTC with `Z` | `"2026-10-02T14:03:11.123Z"` |
| Enums | UPPER_SNAKE_CASE string | `"PARTIALLY_DELIVERED"` |
| Field names | camelCase | `invoiceDate` |
| Nulls | Explicit `null` for absent optional values in responses. In merge-patch requests, `null` means "clear" | |
| Booleans | `true`/`false` | |

- Decimal strings are parsed with `BigDecimal`, with no scientific notation. Scale is validated against the field's precision. A server-side rounding mismatch on an input amount returns `422`.
- References in responses are embedded **summaries**, to save round trips: `"customer": {"id": "...", "code": "C0001", "name": "Acme"}`. Requests send only IDs (`customerId`).

## 12. Authentication on the API

The full specification is in SECURITY.md §3.

- **Browser SPA:** session cookie `__Host-erp_session` (HttpOnly, Secure, SameSite=Lax, Path=/). Every unsafe method needs the CSRF header `X-CSRF-Token`, whose value comes from the `XSRF-TOKEN` cookie that `GET /api/v1/auth/csrf` returns.
- **Integrations:** `Authorization: Bearer erp_pat_<prefix>_<secret>` (personal or service tokens). CSRF does not apply to bearer-authenticated requests. Cookies are ignored on such requests.
- Requests with neither credential reach only `@PublicEndpoint` routes: login, MFA completion, password forgot and reset, invite acceptance and CSRF bootstrap. Health probes live on the separate management port. Every other endpoint answers `401`.
- Unsafe cookie-authenticated requests also need an `Origin` (or `Referer`) from the allowed origins.
- Password fields are taken verbatim (no trimming, `@RawText`) and normalized with NFKC by the server.

## 13. Rate limiting

Response headers follow the IETF RateLimit header draft: `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`. A 429 response includes `Retry-After`. Limits are defined in SECURITY.md §9.

## 14. Async operations

Long-running commands return `202 Accepted` with `Location: /api/v1/companies/{c}/jobs/{jobId}`. These include payroll calculation, report exports, imports, period close and year close.

```json
{ "id": "...", "type": "PAYROLL_CALCULATION", "status": "RUNNING", "progress": {"done": 120, "total": 400},
  "resultUrl": null, "error": null, "createdAt": "...", "completedAt": null }
```

Clients poll with backoff, starting at 1 s and capped at 10 s. An optional server-sent events stream for job updates is a Phase 11 enhancement.

## 15. Transaction boundaries

- Each non-GET request executes as **exactly one database transaction**, which includes the audit records, idempotency record, event publication registry rows and synchronous listener effects (GL postings).
- An action either fully succeeds or leaves no trace. The only trace kept on failure is a failed-login or denied-access audit record, written in a separate transaction on purpose.
- Bulk endpoints such as `POST /…/bulk-deactivate` or imports are either all-or-nothing (≤ 500 items) or async jobs with per-chunk transactions. The job result reports per-row outcomes.
- GET requests run in **read-only transactions** (`SET TRANSACTION READ ONLY`), with the company context set for RLS.

## 16. Files

- Upload: `POST /api/v1/companies/{c}/files` (multipart, field `file`). It returns `{id, filename, contentType, size, sha256}` with status PENDING.
- Attach the file by passing `fileId` to the owning resource's attachment endpoint (`POST /…/{id}/attachments {fileId}`), which activates it. Pending files are purged after 24 hours.
- Download: `GET /…/{id}/attachments/{attachmentId}/content`. This checks the owning entity's read permission, then streams the file or redirects (`302`) to a 5-minute pre-signed URL. It sets `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.

## 17. Endpoint catalogue

Notation: `{c}` = `/api/v1/companies/{companyId}`. **[A]** = requires `If-Match`. **[I]** = requires `Idempotency-Key`. The permission in brackets is the one checked (catalogue in SECURITY.md §4.2). Every list endpoint supports §8. The exact filter allowlists live in OpenAPI.

## 18. OpenAPI and client generation

- The OpenAPI document is generated by springdoc. Each module has its own tag. Every operation's description lists its permission (`x-permission`), whether `If-Match` and `Idempotency-Key` are required (`x-requires-if-match`, `x-requires-idempotency-key`), and its possible error codes.
- The frontend generates its types with `openapi-typescript` during the build. CI fails if the committed `frontend/src/api/schema.d.ts` is stale.
- An **API contract test** in CI verifies that every controller method has a permission annotation, and that every action endpoint requires `If-Match`.
